Containerization: A Comprehensive Overview

Containers are executable units of software that package application code alongside its necessary libraries and dependencies.

This standardized packaging allows the software to run consistently anywhere, whether on a desktop, in traditional IT infrastructure, or in the cloud.

Unlike Virtual Machines (VMs), containers are incredibly small, fast, and portable because they do not require a guest Operating System (OS) in every instance. Instead, they efficiently leverage the features and resources of the underlying host OS.

While tools like Docker and Kubernetes are highly popular today, container technology has been evolving for quite some time.

The foundation was laid in 2008 when the Linux kernel introduced control groups (cgroups), which paved the way for modern container runtimes like Docker, Cloud Foundry, and Rocket.

The Limitations of Virtual Machines (VMs)

To understand the value of containers, it helps to look at the traditional VM deployment model.

In a VM setup, the physical hardware runs a host OS and a hypervisor. If a developer wants to deploy a simple, lightweight Node.js application, they must spin up a VM.

Every single VM requires its own guest OS, along with a full set of binaries and libraries. This heavily bloats the deployment.

For example, a Node.js runtime and application might only be 15 megabytes, but the required Linux VM could easily exceed 400 megabytes.

When scaling this application, the entire bloated VM—including the duplicate guest OS—must be copied every time. This rapidly consumes all available hardware resources.

Furthermore, developing an application on a local machine and pushing it to a production VM often leads to environmental incompatibilities (the "it works on my machine" problem), hindering agile DevOps and continuous delivery.

How Containerization Works

Containers solve these inefficiencies through a streamlined, three-step process.

First, a manifest is created to describe the container (such as a Dockerfile).

Next, this manifest is used to build an image (such as a Docker image or Rocket ACI).

Finally, that image is run as a container, which holds only the runtime, libraries, and binaries specifically needed for the application.

In a containerized architecture, the physical hardware still runs a host OS, but the hypervisor is replaced by a container runtime engine (such as the Docker engine).

Because containers do not require a guest OS, they are exceptionally lightweight.

When you scale a containerized application, you are only duplicating the app and its specific libraries, which consumes significantly fewer resources compared to VMs.

Enabling Cloud-Native Architectures

Containers perfectly support modern, cloud-native microservices.

For instance, if a developer wants to add a separate Python application to interface with a third-party cognitive API, they do not need to spin up a massive new VM or awkwardly combine both apps into an existing VM (which would prevent them from scaling independently).

Instead, they can simply deploy a lightweight container for the Python app.

Any remaining hardware resources are efficiently shared among all running container processes.

If one container is not utilizing its CPU or memory, those resources instantly become accessible to other containers running on that hardware.

Ultimately, containers provide superior portability, highly efficient scaling, and the foundational architecture necessary for agile DevOps and seamless Continuous Integration and Continuous Delivery (CI/CD).
